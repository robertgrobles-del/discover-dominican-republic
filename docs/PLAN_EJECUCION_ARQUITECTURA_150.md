# Ejecución del Plan Maestro de 150 Mejoras

**Fuente:** `PLAN_MAESTRO_DEFINITIVO_ARQUITECTURA.md` (documento de planificación entregado por el usuario).  
**Fecha de línea base:** 2026-09-30.  
**Prioridad acordada:** migrar primero el backend del monolito modular a microservicios.

## Criterio de estado

- **Implementado:** hay evidencia directa en código, configuración o contrato del repositorio.
- **Parcial:** existe una parte, pero falta automatización, integración, medición, configuración de producción o propiedad independiente.
- **Por validar:** no se encontró evidencia suficiente en la revisión inicial; no significa que el elemento no exista fuera del repositorio.
- **Pendiente:** trabajo conocido sin implementación suficiente.

Este documento es una línea base, no una certificación de producción. Los estados se cambian sólo con evidencia. Las iniciativas que dependen de credenciales, contratos externos, contenido institucional o decisión de producto se mantienen explícitamente bloqueadas hasta obtener esos insumos.

## Orden de ejecución

1. **Arquitectura de microservicios (bloque prioritario):** diseñar límites de dominio, propiedad de datos, contratos, gateway, identidad entre servicios, observabilidad y topología de entornos. Se seleccionó el subdominio meteorológico como piloto, no el módulo `live` completo; falta extraer `weather_snapshots`, administración y refresh a almacenamiento/despliegue propios. Detalle: [`ARQUITECTURA_MICROSERVICIOS.md`](ARQUITECTURA_MICROSERVICIOS.md) y [`DEPENDENCIAS_DATOS_INVENTARIO.md`](DEPENDENCIAS_DATOS_INVENTARIO.md).
2. **Contenido/directorio:** extraer catálogo y CMS, migrar datos, asegurar compatibilidad de URLs, SEO, traducciones y workflow editorial.
3. **Transacciones:** extraer reservas, comercio y pagos; migrar JWT, catálogo y escrituras; habilitar cobros sólo con pasarela tokenizada e idempotencia.
4. **Gamificación, comunidad y moderación:** extraer según el mapa de eventos y datos; el servidor sigue siendo autoridad para XP, monedas y decisiones de moderación.
5. **Monetización y analítica:** extraer anuncios, afiliación, operadores y analítica con consentimiento, atribución y controles fiscales aplicables.
6. **Operación transversal:** staging, backups/restores, alertas, seguridad, resiliencia, rendimiento y despliegue independiente por servicio.

## Reglas de migración

- No convertir los módulos actuales en microservicios mecánicamente: agrupar por dominio y dependencias reales.
- Mantener temporalmente el monolito como dueño de los dominios aún no extraídos.
- Un servicio extraído no consulta ni modifica tablas de otro servicio. Toda migración de datos necesita reconciliación y rollback.
- Mantener `/api/v1` compatible mediante el gateway hasta migrar consumidores.
- No enviar datos de tarjeta al backend propio; usar token de pasarela.
- Actualizar este registro y el README en cada fase con enlaces al cambio, evidencia, riesgo y decisiones pendientes.
